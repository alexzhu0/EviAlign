# Optional Jev shadow scoring for the synthetic business sandbox

Date: 2026-10-14
Status: draft for written-spec review; no retained implementation authorized by
this document alone.

## Intent and scope

The user approved moving the successful throwaway Jev experiment toward an
optional shadow scorer in the separate `agentharness-business-sandbox` runtime.
Its purpose is to observe whether a model's proposed business action matches the
user's intent, including explicit read-only limits and missing parameters.

Implementation, tests and runtime documentation belong to the sandbox's separate
review and commit unit. This AgentHarness document records the integration
boundary; it does not add networking to AgentHarness evidence validation.
AgentHarness continues to emit `result_status: not_executed` for its evidence.

## Evidence from the spike

The 2026-10-14 experiment froze the cases, criteria, runner digest and confidence
threshold before 24 live OpenRouter requests. Requested model:
`typesafe/jev-1.13`; returned model: `typesafe/jev-1.13-20260917`.
The original temporary artifacts are in the session's
`/tmp/agentharness-jev-spike-20261014-SefXfx/` directory; their continued
availability is not guaranteed and they are not repository assets.

The freeze digest was
`c547d252f1ee789293e74146b34a455234b93ab6d6a201da728072768c706fe9`.
Original classification matched hand-written labels in 21/24 cases: 8/8 fits,
8/8 overreach and 5/8 unclear. All eight unclear cases received a review hint
under the preselected 0.8 confidence threshold. No tool ran. Cost reported by
OpenRouter was USD 0.00067452; end-to-end median was 974.78 ms and p95 was
1363.47 ms. These are small synthetic-sample observations, not latency promises,
production acceptance or proof of calibration.

The spike's baseline used deliberately synthetic permit records to exercise
receipt correlation. It did not run or assess the sandbox authorization engine.
The 24 cases are now seen regression examples and cannot become a new blind
acceptance set.

## Alternatives and selected approach

1. Continue a standalone offline/replay experiment. This has the least runtime
   coupling, but does not observe proposals generated by the sandbox's current
   conversation loop.
2. Add an opt-in observation hook around that existing conversation loop.
   This is selected: it observes actual proposals and keeps authorization,
   execution, transactions and idempotency entirely in the sandbox.
3. Enforce model judgments as an execution gate. This is deferred and outside
   this design; a hint is not an approval or a denial.

## Runtime flow

Add one optional judge parameter to `Conversation`, defaulting to disabled.
The current planner still produces an untrusted proposal. After existing
proposal-shape validation and repeated-read checks, score that proposal once
before `runtime.act`. Do not score `finish`, malformed proposals or stalled
duplicate reads.

Build state from the current user request, a bounded selection of prior user
requests, the current proposal and explicit tool meanings. Prior messages are
context rather than instructions that override the latest request. Include only
minimal synthetic identity facts needed to interpret phrases such as "my
orders". Do not transmit full result rows, the database, session cookies,
credentials, operator snapshots or raw authorization history. When required
context cannot be represented, record a review hint or a skipped assessment;
do not invent facts. Any optional document excerpt is explicitly untrusted and
cannot confer user intent or alter criteria.

After the judge returns or fails, recheck current trusted context binding before
calling `runtime.act`, just as the loop already does after planner calls.
Revocation or context changes during the extra network wait must take the
existing `context_changed` path and clear history.

Keep assessments in a separate top-level `jev_shadow` list, indexed by current
turn proposal position and bound to canonical request/proposal digests. Do not
put them into evidence receipts, runtime action logs, planner observations or
conversation history. They must not affect authorization, action selection,
execution, transaction results, answers derived from runtime observations or
replay. `human_review` means a recorded recommendation in this shadow mode;
it does not pause execution or assert that a human reviewed the action.

## Judgment contract and local policy

One `choice` question defines exactly three labels: `fits`, `overreach` and
`unclear`. Version and hash instructions, criteria, tool descriptions and the
state projection. A changed rubric creates a new evaluation version.

Use the experiment's 0.8 floor initially as an observation policy, not as a
calibrated production threshold. Low confidence or `unclear` produces
`human_review`; confident `overreach` produces `flag_overreach`; confident
`fits` produces `no_flag`. None grants runtime permission.

Validate bounded JSON, duplicate keys, exact question identity, supported model
identity, label membership, finite probabilities in [0, 1], probability sum and
winning label consistency. Treat transport, timeout, model mismatch, malformed,
oversized and internal failures as unavailable assessments with fixed bounded
codes. Never convert a failed assessment into a successful judgment. Only the
optional observation is unavailable; normal execution remains governed by the
existing independent runtime.

Store only validated model identity, label, probability distribution, confidence,
review hint, rubric digest, proposal/request digests, duration and available
validated usage metadata. Do not add raw prompts, host paths, exception text or
provider messages to output. Bound assessments to four per turn and existing
conversation limits; use no retries or alternate-model fallback.

## Opt-in configuration and network

Expose `--jev-shadow` on existing `ask`, `serve` and `test-model` commands.
Without the flag, do not read OpenRouter credentials or make Jev requests;
preserve existing output shapes and offline behavior. `world`, `act`, `test`
and `compare` remain deterministic and do not invoke Jev.

Reuse the user-authorized `OPENROUTER_BASE_URL` and `OPENROUTER_API_KEY` from the
existing ignored AgentHarness `.env`, resolved through the sandbox's established
source-directory convention. Never copy, source or print the file. Require a
bounded regular non-symlink file, unique nonempty target entries and no credential
expansion. The adapter uses standard-library HTTPS, the exact official
`https://openrouter.ai/api/alpha/decisions` endpoint, redirect rejection and a
bounded response. Accept the usual OpenRouter `/api/v1` base by normalizing it
to the Decisions endpoint; reject credentials in URLs or nonofficial hosts.

Pin requested `typesafe/jev-1.13` and the observed returned version
`typesafe/jev-1.13-20260917`; future model-version changes need a new freeze.
Use a 10-second timeout, one request per eligible proposal, maximum 16 KiB
outbound state/question envelope and 64 KiB response. Enabling the option must
disclose that synthetic requests/proposals go to OpenRouter and consume credits.
Jev request counts and usage are separate from existing planner accounting.
No new SDK or background worker is required.

## Verification and acceptance

Use failing offline regressions before implementation. Tests must demonstrate:
disabled mode performs no credential read or Jev call; expected hints and errors
do not change independent runtime outcomes or counters; context revocation
during scoring prevents execution; assessments stay out of planner history;
output and response bounds hold; bad probabilities, identities, endpoints,
redirects and credential files fail at the observation boundary without leaks.

Run the sandbox's complete unit/HTTP suite and both 60-case deterministic arms,
plus AgentHarness's repository-required checks. Review the two repositories
separately before integration. Any live acceptance run must freeze new unseen
cases, rubric, model and code revisions before calls, retain the original
results, record usage limits and distinguish classification accuracy from
threshold-based hints. Existing paid DeepSeek suites are not rerun merely to
validate the adapter.

Acceptance requires default-off compatibility and observation-only behavior,
not a target semantic accuracy invented from this 24-case experiment. Real
data, production writes, automatic blocking/allowing, provider failover and
runtime authorization changes require separate designs and approvals.
